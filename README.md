# ERTHPORTAL

## Architecture

GitHub Pages hosts the frontend. Supabase Free provides username/password authentication, account profiles/status, and protected Edge Functions. Google Sheets remains the employee-data source. Users access assigned PLANTILLA sheets through the `google-sheets-api` Edge Function, which authenticates to Google as a server-side service account; users do not need to authorize Google individually.

Account passwords are managed by Supabase Auth and are never stored in the profiles table or GitHub. Default accounts use a one-time numeric password of at least 8 digits and must choose a username and a new password before continuing. New passwords must be at least 8 alphanumeric characters and include both letters and numbers. `inactive` accounts cannot sign in; the login page directs locked users to the administrator.

## Supabase Setup

1. Create a Supabase project on the Free plan.
2. In **SQL Editor**, run `supabase/migrations/202610020001_profiles.sql`, `supabase/migrations/202610050001_profile_photo_sheet.sql`, `supabase/migrations/202610050002_dashboard_assignments.sql`, `supabase/migrations/202610070001_master_admin_client_scopes.sql`, `supabase/migrations/202610070002_regular_admin_account_scopes.sql`, `supabase/migrations/202610080001_case_sensitive_usernames.sql`, `supabase/migrations/202610080002_user_online_presence.sql`, and `supabase/migrations/202610080003_dashboard_client_urls.sql` in that order.
3. Deploy the protected `admin-users` and `google-sheets-api` Edge Functions. With the Supabase CLI installed, run `supabase login`, `supabase link --project-ref YOUR_PROJECT_REF`, `supabase db push`, `supabase functions deploy admin-users`, and `supabase functions deploy google-sheets-api` from this repository. The functions use Supabase's server-side `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; never put the service-role key in the page or GitHub.
4. Bootstrap the first administrator in Supabase **Authentication → Users**: create and confirm a user with email `admin@accounts.erthportal.invalid` and a strong password. Copy that Auth user's UUID. In SQL Editor, insert its profile, replacing the UUID and Google email:

	```sql
	insert into public.profiles (id, username, display_name, google_email, client_name, client_names, is_master_admin, role, status)
	values ('AUTH_USER_UUID', 'admin', 'Portal Administrator', 'admin@example.com', 'My spreadsheets', '{}', true, 'admin', 'active');
	```

5. Paste your live values into the page config in `index.html` using the global variables `window.ERTHPORTAL_SUPABASE_URL` and `window.ERTHPORTAL_SUPABASE_ANON_KEY` before the app script runs. The anon/publishable key is public and safe to include with RLS enabled; never use the service-role key. `window.ERTHPORTAL_GOOGLE_CLIENT_ID` is only needed if an administrator uses the optional personal-sheet connection flow. You can also define these values before `index.html` loads in a hosted environment if you prefer to keep the values outside the source file.
6. Publish the updated frontend and `supabase` folder to GitHub Pages.

Usernames are mapped to internal, lowercase Supabase Auth addresses ending in `@accounts.erthportal.invalid`; users sign in with their registered username and password, not that generated address. Username matching is case-sensitive, so capitalization must exactly match the value registered in the profile. Usernames remain unique regardless of capitalization. Admins reset passwords by username; the user receives an 8-digit temporary password and must choose a username and replacement password at next sign-in. New passwords must be at least 8 alphanumeric characters and contain both letters and numbers. Users can also update their own username in **My Account**. The login page can remember a username on the current device, but never stores a password. “Forgot password?” asks for the username and explains that the administrator must issue a temporary password; password recovery is not allowed from a username alone.

An authenticated portal session is retained only in the current browser tab so refreshing the page restores the signed-in user and last-open dashboard. Closing the tab ends that browser session. The portal automatically signs users out after 30 minutes without activity.

The profile with username `admin` is the Master Admin. Set `is_master_admin = true` when bootstrapping that profile; the migration promotes an existing `admin` username automatically. Only the Master Admin can create and manage accounts or assign dashboard spreadsheet URLs. Regular Admins can manage only User accounts assigned to them; they cannot view or change dashboard spreadsheet assignments. When creating a Regular Admin, the Master Admin selects its allowed clients and the existing User accounts it may administer using checkboxes. The managed-account checkboxes limit which User profiles that Regular Admin can manage, including their account status; they do not grant additional spreadsheet data access by themselves. The Regular Admin profile's `client_name` is `ADMIN`; its actual client scope is stored in `client_names`. User accounts are restricted to one client. To supply the account and dashboard client dropdowns, assign the Master Admin's HR EMPLOC spreadsheet to **HR EMPLOC MONITORING**; the portal loads distinct client names from `G1vcode!C3:C`. For initial setup, the Master Admin can save that HR EMPLOC URL without selecting a client. Dashboard assignments store client scope per dashboard. Regular Admins use client-specific URLs selected before a dashboard opens; shared workbooks can be assigned to multiple clients by entering the same URL for each client. Vacancy and HR EMPLOC reads filter their client columns (VACANCY column C; G1N column B) against the selected client.

The Master Admin's **Preview User Portal** can open both User and Regular Admin accounts. While previewing, dashboard assignment controls remain available because the signed-in Master Admin remains the actor; saved spreadsheet URLs are assigned to the selected or previewed account, not the Master Admin. For each Regular Admin dashboard assignment, the Master Admin selects allowed clients and enters a corresponding spreadsheet URL for each client. When a Regular Admin opens a dashboard assigned to multiple clients, the portal requires a client choice before loading and uses only that client's spreadsheet and data scope for reads and updates. In PLANTILLA, VCODE MASTERLIST, VACANCY MONITORING, and HR EMPLOC MONITORING, a client selector beside the search field lets the administrator switch among assigned clients without leaving the dashboard; changing clients reloads records from that client's assigned spreadsheet.

Admins add users from the dashboard's **Add User** control. The account-management dialog uses a spacious layout and checkboxes for Regular Admin client and managed-user selection. Selecting existing User accounts for a Regular Admin to manage is optional; if none are selected or available, the Regular Admin is created without managed User accounts. A **Refresh** button in the dashboard header reloads the current dashboard data in place and keeps the signed-in session and page open. Text values entered in dashboard record-update forms are converted to uppercase before they are saved to Sheets. The account list shows current profile photos and administrators can set an individual status or select multiple accounts and bulk-apply `active`, `inactive`, or `default` status. Setting `default` requires the user to set a username and password on next sign-in. Changing a user to `inactive` does not remove or change their spreadsheet assignments; those URLs remain saved and become usable again if the account is reactivated. Deleting the account removes its assignments. The initial password is set by the admin, and dashboard spreadsheet URLs and client scopes are assigned per account from each dashboard's **Assign spreadsheet URL to user** action. The assignment migration and updated Edge Functions must be deployed for these per-user settings to sync across devices.

In **PLANTILLA**, User accounts can use **Newly Hired** to set blank `PLANTILLA!AH9:AH` status cells to `NEWLY HIRED` for rows with a VCODE in column B on their assigned spreadsheet. Existing values and formulas are left untouched. A progress modal appears immediately; the server reads eligible cells and sends one batched spreadsheet write instead of many sequential calls. After saving, the visible table updates immediately and refreshes from the spreadsheet in the background, while a completion popup reports the number marked. If no eligible blanks exist, it displays a no-available-cells message. The User PLANTILLA dashboard also checks column B from row 9 for duplicate VCODE values and, when found, displays a table with VCODE, EMPLOC, FULLNAME, OUTLET, and HC for each matching row. The **DUPLICATE CHECKER** button reopens the latest duplicate results; if none were found, it reports that no duplicate VCODEs are available.

The **INACTIVE** archive setup is available from the Master Admin dashboard picker only. Save its destination spreadsheet URL there; the assignment is attached to the Master Admin account, and users cannot access it. When a User updates a PLANTILLA record whose AG separation date is set and AH status is `AWOL`, `BACK OUT`, `ENDO`, `FLOATING`, `RESIGNED`, `TERMINATED`, `TEMPORARY STORE CLOSED`, `PERMANENTLY STORE CLOSED`, or `MOVEMENT`, the service copies that row's A:AR values into an explicitly selected next available A:AR row of the archive's `INACTIVE` tab, appends its VCODE to column B of the User's assigned `VACANCY` tab, then deletes the entire source PLANTILLA row. A completion popup follows; if any transfer step fails, the source row is retained and the error explains whether a safe retry can finish it. The service avoids duplicating matching VCODE entries on retries and does not overwrite an existing archive row with different data. Share edit access to each spreadsheet with the configured Google service account.

In **FOR APPROVAL**, the account with username `ANNIE` cannot select records or use the **Approved** action. This restriction is enforced in both the portal UI and the `google-sheets-api` Edge Function; other administrator accounts retain the existing approval access.

The **VCODE MASTERLIST** dashboard reads the assigned spreadsheet's `VCODE` tab starting at row 3. Its table shows VCODE (A), Outlet (B), Position (D), and HC (L); **View** opens a read-only side drawer with Area (E), Restday (F), Schedule (G), Designation (H), Penalty (I), Coordinator (J), HRCO (K), Chain (M), and City (N).

The **PLANTILLA SUMMARY** dashboard combines the account's assigned **VCODE MASTERLIST** and **PLANTILLA** spreadsheets. It lists unique positions from `VCODE!D3:D`, sums required HC from `VCODE!L3:L` for each position, sums actual HC from `PLANTILLA!AC9:AC` grouped by the matching PLANTILLA position in column G, and calculates GAP as required HC minus actual HC. A total row at the bottom sums the required HC, actual HC, and gap columns. Assign both source dashboard spreadsheets to the account and client; the summary's two assign buttons open the corresponding source assignment editors.

**VACANCY MONITORING** reads the assigned `VACANCY` tab from row 5, displays VCODE (B), Outlet (G), Position (H), HC (I), Date of Vacant (O), and Aging (R), and uses VCODE as the unique update key. Its drawer title is the VCODE and it edits Date of Vacant (O), Lastname (K), First Name (L), Middle Name (M), Contact Number (N), Date Onboard (P), Reliever (U), HRCO Remarks (W), Coordinator (AD), and Deployed By (AF); HC and Aging remain in the table only. Updates write only fields the user changed, as separate single-cell ranges in one Sheets request to the uniquely matched VCODE row; changes to formula cells are rejected, preserving formulas in untouched cells. The table and drawer update immediately after a successful save while the full table refreshes in the background. Coordinator and Deployed By choices come from `Deployer!A2:A`. **HR EMPLOC MONITORING** reads `G1N` from row 9 and displays VCODE (G), Fullname (K), Position (AB), Onboard Date (V), Aging (X), Outlet (AC), and HC (Z); it only returns rows where `G1N!B9:B` matches the assigned profile's client name. Its one-line drawer heading combines VCODE and Fullname, and its drawer reads and updates only HRCO Remarks (J), matched by VCODE. VACANCY MONITORING, HR EMPLOC MONITORING, and FOR APPROVAL show TOTAL HC summed from the currently visible table rows, so the total responds to search. Drawer title/section/summary backgrounds are transparent. Dates use date inputs when editable and display in uppercase month-day-year format.

When **Update remarks** saves HRCO remarks containing `BACKOUT`, `BACK-OUT`, or `BACK OUT`, the service copies the full `G1N` A:AC row to the assigned HR EMPLOC spreadsheet's `back-out` tab and appends its VCODE to column B of the assigned `VACANCY` tab for the matching client. It then deletes rows from `On Board Database` only when both its column B VCODE matches `G1N` column G and its column AL value matches `G1N` column K on that same row. After verifying the destination writes and On Board cleanup, it deletes the source `G1N` row. If a step fails, the source is retained, the error explains what happened, and retrying safely reuses already verified destination copies.

**FOR APPROVAL** reads rows from the assigned spreadsheet's `VACANCY` tab starting at row 5, scoped to the dashboard's assigned clients. A row is included only when all of K, L, M, N, O, P, U, V, W, and AF are nonblank. It displays Client (C), VCODE (B), Outlet (G), Fullname (AL), HC (I), Date Vacant (O), and Aging (R), with search, a visible-row TOTAL HC, refresh, and multi-row selection. User accounts can view pending rows but cannot approve; Master Admins and Regular Admins can use the **Approved** control. Approval copies each selected VACANCY row to the `On Board Database` tab in the same spreadsheet, leaving columns O and AA untouched, then copies source columns Z, C, K, L, M, Y, and B to columns A:G of the next available row in the account's assigned HR EMPLOC spreadsheet `G1N` tab. After verifying both destination copies, it locates the unique source record by VCODE in `VACANCY` and deletes that entire row; deletion is keyed only by VCODE, not by comparing all row values. If the first row deletion leaves the VCODE present, it clears that matched row's non-formula cells and retries deleting the whole row; formula columns O and AA are left for their array formulas. Safe retries recognize matching destination copies. Share edit access to both spreadsheets with the configured Google service account.

After changing `google-sheets-api`, deploy the updated function with `supabase functions deploy google-sheets-api` from the repository root for the new dashboard reads and writes to work.

## Google Sheets service account setup

To make assigned PLANTILLA sheets plug-and-play for users, configure the service account once:

1. In Google Cloud, enable the Google Sheets API and create a service account. Create a private key for it and keep the downloaded key out of the repository.
2. In Supabase **Project Settings → Edge Functions → Secrets**, set `GOOGLE_SERVICE_ACCOUNT_EMAIL` to the service account email and `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY` to the private key's `private_key` value. These credentials must remain server-side; never add them to `index.html`, GitHub, or a user account.
3. Share each private spreadsheet with that service account email as an **Editor**. This one-time file sharing lets the portal read and update the assigned sheet without prompting each user to authorize Google. Do not make employee data public.
4. Deploy `google-sheets-api` as shown above. In the portal, assign each user's spreadsheet URL to the PLANTILLA dashboard. The sheet must contain a `PLANTILLA` tab.

The Edge Function checks the signed-in portal account and only serves spreadsheets assigned to that account. Administrators previewing a user portal are restricted to that user's assignment as well. The function reads rows 9 onward and updates only Rate (H), Separation Date (AG), and Status (AH).

The optional administrator-only **Connect my sheet** flow still uses browser-based Google OAuth. If using it, set a Web OAuth client ID in `window.ERTHPORTAL_GOOGLE_CLIENT_ID` and add `https://ceris-system.github.io` as an authorized JavaScript origin. Ordinary users do not need this OAuth client or individual Google authorization for assigned PLANTILLA access.

- Supabase project URL: `https://<project-ref>.supabase.co`
- Supabase anon key: from `Project Settings → API`
- Google service-account email and private key set as Supabase Edge Function secrets
- Each private assigned PLANTILLA sheet shared with the service-account email as Editor
- Optional Google OAuth client ID only if an administrator uses **Connect my sheet**

Branding URLs:

- Homepage: `https://ceris-system.github.io/ERTHPORTAL/`
- Privacy policy: `https://ceris-system.github.io/ERTHPORTAL/privacy.html`
- App name: `ERTH PORTAL`
